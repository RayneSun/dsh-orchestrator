# interaction-core 与可配置 Worker：实施说明

Alpha 实施方案，尚未实现。配套：[《interaction-core 开发者接入协议 v1》](worker-reporting-protocol-v1.md)。本次改造一并交付独立 Core、Orchestrator 接入和 GenUI 运行时切换。PPT 仓库只作参考，由维护者根据协议另行迁移。Orchestrator 基线：`37140d5`（0.3.24）。

## 1. 依赖与职责

| 所有者 | 职责 |
|---|---|
| **interaction-core** | 独立 DSH 子 Core 插件。交付版本化字段契约、工具侧 SDK、一个宿主服务和一套客户端渲染器。负责登记问题、绑定真实调用、校验并接收答案、等待与取消、媒体加载、嵌入式卡片及可复用卡身。也提供非阻塞报告通道，以及 `create_ui`、只读卡存储和 `dsh-ui` 引用渲染。 |
| **Orchestrator** | 依赖 Core。负责 Worker 目录与派发、执行绑定、任务状态持久化、投递和自己的任务卡。消费一条带版本的问答及报告数据流。用户点击任务的待答入口后，弹框内挂 Core 的问题卡身；弹框外壳和入口位置仍由 Orchestrator 决定。 |
| **通用 Worker / 外部 Worker** | 在需要交互的工具内声明问题和预览，调用 SDK 并消费结构化答案；在需要更新进度时调用 SDK。无需实现卡片、RPC、轮询、媒体端点或双路同步。 |

```text
PPT 业务工具 ───┐
通用 Worker ────┴──→ Core 工具 SDK → Core 宿主运行时 ← 第一份有效答案
                                           │  │          ↑     ↑
                              问答及报告流 │  └→ 同一请求/同一卡身
                                           ↓             │     │
                                     Orchestrator      Worker  看板弹框
                                      任务/投递        会话内嵌 （点击后）
```

Core 在没有 Orchestrator 时也能在所属会话提问与显示卡片。Orchestrator 不出现在 Core 或外部 Worker 的依赖里。推荐同一包交付 DSH 插件和 SDK/客户端入口；两个消费者都明确依赖兼容主版本，每个 DSH 宿主只激活一个 Core 服务。SDK 只调用已激活的服务，禁止每个依赖者在自己的 bundle 中创建等待表。实际装载方式要用目标版本的 DSH 验证：「包已安装」和「Host + Client 已激活」是两件事；插件启用关系应由宿主配置明确，不能假定 npm 安装会替用户启用。核心只运行于同一 DSH 宿主，复用平台会话和鉴权，不用 Redis，不合并 PPT 的业务代码。只读卡引用由 Core 在会话的 Markdown 渲染位置接管。

## 2. 设置页与可派发目录

在 `src/client/settings-card.tsx` 的「插件管理 → orchestrator → 配置」加入「可派发 Worker」区域。显示内置 `common`（只读，绑定 `may-orchestrator-worker`），允许用户添加、编辑、启用/停用和移除专用 Worker。设置按当前 DSH profile 持久化，复用已有授权配置通道和可编辑/只读处理；列表是受 Host 校验的结构化设置，由一次成功保存整体更新。正常编辑即时影响下一次提示词渲染和派发，不用重启 Web 或重挂 Lead 工具。无可用预设时给清楚提示；不安装新插件，不让用户输入源码路径或凭据。

| 字段 | 约束 |
|---|---|
| `id` | 稳定路由 ID，1–64 字符，小写字母/数字和短横线、点分隔，例如 `cmjt.ppt`，形状 `^[a-z0-9]+(?:[.-][a-z0-9]+)*$`。保留 `common`、历史内部名 `general`。重复拒绝。 |
| `name` | 界面及提示词显示名，去空白后 1–40 字。 |
| `description` | 路由介绍，去空白后 1–160 字，说明擅长及适用场景，不当系统指令。 |
| `preset` | 已加载且可用于新建根会话的 DSH agent preset ID，设置页从宿主已加载列表选取；不允许 Lead 自己的 preset 或编排器保留的 preset。 |
| `enabled` | 布尔值，新增默认 `true`。停用保留配置，移除保留历史任务。 |

- 服务端同时处理格式、重复、预设选择合法性和授权，失败保留原配置；显示名与介绍用有界、单行、安全序列化的数据行放进提示词。列表读取时保留后来失效的配置，在 UI 标注「预设未加载」等原因；允许编辑、停用或移除这些历史配置。启动顺序、预设删除/恢复由实时目录重新判定，绝不从 npm 包名或已安装工具猜测。
- `src/modes.ts` 演进为目录与解析边界。**已配置、可派发、支持上报是三件事。** `common` 始终内置；专用项启用且对应 preset 当前存在并可装配时可供派发。预设未接入 interaction-core 时仍可派发；整单结算走派发注入的工具，业务进展及问答只有实际调用 Core 才会出现。设置页解释这一点，不另加需要外部插件注册的握手。
- 专用 ID 和绑定的 preset 不能在同一注册项上直接改绑；要换预设，注册新 ID。新专用会话持久化当时绑定的 preset ID，以防移除后复用同 ID 时旧会话被悄悄切换。保留现有 lead/worker 分隔和递归派发禁用；外部预设按自身配置运行，不因为入目录自动继承通用 Worker 的 `danger-full-access`、通用 persona 或 GenUI 覆盖。专用模式可在自己的业务工具里调用 Core，不为此放开嵌套编排策略。

## 3. `orchestrator_dispatch.type` 与 Lead 提示词

对模型只暴露 `type`（可选字符串）。既有 `mode` 是当前工具字段，切换时替换它，不暴露第二个同义参数；显式收到旧 `mode` 时返回字段错误，不能因解析器丢掉该字段而误派 `common`。每次调用仍派发一条任务；多 Worker 指 Lead 可为不同事项分别调用并行派发，不增加批量数组。DSL 描述写「新建省略用 common，专用从当前可派发 Worker 列表复制 ID，复用省略沿用原 Worker」，Zod 校验字符串形状，宿主校验实际可选集合；不能只校验格式。动态名单走 Lead 的 required context（`interpolate:false`），不把实时配置硬编码为静态 `enum` 或复制到 persona。每次提示词构建从同一目录读取 `id / name / description`，例如：

```text
可派发 Worker（orchestrator_dispatch.type）
common — 通用执行：文件、开发、联网、文档与定时任务
cmjt.ppt — PPT 工作流：策划大纲、确认风格、编辑和生成演示文稿
```

先按 roster 判断是不是同一事项，接着才在新建时按介绍选择专用 Worker；普通执行默认 common。`cmjt.ppt` 仅为示例，只有在设置中注册且当前可用时才出现。保留常规 Worker 的工具/技能能力上下文及现有正文直答规则。若 Lead 用了已经失效的提示词快照，宿主返回中文错误，允许模型根据当前目录修正；禁止把明确指定的专用请求静默降给 `common`。

| 调用 | 决策 |
|---|---|
| 新建，省略 `type` 或明确 `common` | 选择内置通用 Worker，持久化仍可用 `Conversation.mode = general`。 |
| 新建，`type: 'cmjt.ppt'` | 必须能在宿主当前目录解析；从选中的同一条定义写预设并实际 `agentPresets.mount`。未知、停用或预设不可用时拒绝。 |
| 复用，带 `conversationId`，省略 `type` | 按存量 `Conversation.mode` 解析并检查归属、当前可用性及预设绑定；通用记录无 `mode` 或值为 `general` 时解析为对外 `common`。 |
| 复用，显式 `type` | 先把存量模式归一成对外 ID；一致才继续。不同、预设绑定不匹配或已下架则拒绝，保留原会话、任务和工作区。 |

```json
{
  "type": "cmjt.ppt",
  "subject": "季度经营复盘",
  "workspaceName": "quarterly-review",
  "prompt": "制作季度经营复盘 PPT，涵盖业绩、问题和下季度计划。"
}
```

保护顺序：在建目录、写任务、打断正在运行的任务前完成校验；串行路径内确认配置未变。若实际挂载时预设恰好消失，走现有启动失败结算，不偷偷重试成其他预设。停用或删除只阻止新派发和继续派发；已运行且仍能访问原预设和工具的任务允许按原绑定结算。若所需宿主能力实际撤销，结束相关等待并明确失败。历史记录（包括未知的历史模式）可读；持久化 `mode` 验证稳定 ID 形状，另由实时目录决定能否运行。冷恢复沿用现有显式配置失败路径，不能降为通用或复用不匹配的 preset。看板/roster 可显示已归档或当前不可用的 Worker，Lead 的可派发列表只包含可用项。无需清库；如旧二进制不能解析新字段，说明同版部署与备份回滚。

## 4. 两个入口，一份作答状态

1. 工具在真实执行上下文里调用 `ask`。Core 先校验卡片和素材引用；生成 `requestId`，从宿主绑定来源会话、调用和可选管理执行代次，写入 `pending`。同一次调用可发多题或按业务顺序再问；每次 `ask` 生成新 ID。
2. **Worker 会话**：默认在工具调用所在位置内嵌问题卡，复用 PPT 的卡片层级、正文、图片放大、动作区、加载状态与可折叠的回执。以 `dsh-ppt-workflow/client/interaction.jsx` 的工具视图接法和 `client/Card.jsx`、`client/cards.css`、`client/ImagePreview.jsx` 为只读交互参考。Core 提供桥接层；调用方最多声明哪些工具名承载交互，无需编写组件。会话内可点击图片放大或把整张问题卡展开到会话弹框；弹框和内嵌卡共用同一请求，不产生第二个等待。多入口是同一个问题的多个视图，无需工具逐个推送 UI。首个工程验证点是在目标 DSH 上让两个不同插件的工具都挂同一个 Core 视图：优先用宿主提供的通用锚点；若只支持按工具名键控的 `tool.call.toolview`，由 Core 以声明式注册复用同一实现。处理键冲突时明确报错，并在迁移时移除原业务卡绑定。
3. **Orchestrator**：只订阅所属执行的读模型。`requestId` 源自 Core，任务里仅存必要的投影和关联。现有待答入口点击后打开 Orchestrator 管理的弹框，嵌入同一 `QuestionCard`，其数据、权限、媒体读取和提交仍走 Core。弹框关闭不取消问题；其他入口作答时，弹框关闭或切换为明确的已处理回执，不能继续提交。不开新任务卡样式，不自动在 Lead 聊天正文再插一份问题。
4. Core 以单个请求为粒度串行仲裁：校验当前用户、请求归属、代次、版本与整批答案；**只有第一份有效答案**能把 `pending → answered`。无效答案不占用名额，重复提交返回已处理状态，原 `ask` 只继续一次。客户端成功响应、重新打开和断线重连都以 Host 快照为准。
5. 用户手动停止、工具 Signal 取消、改单撤销代次、到期、Core 卸载都让不可继续的请求离开 `pending`。关弹窗、切会话或暂时断网不取消。首版 `ask` 只保证同一运行中的工具等待；进程重启按中断收敛，不重建 Promise。历史里可留只读回执。一个任务有多个待答请求时，最后一条离开待答、且任务仍活跃，才清除 `input_required`；旧任务事件不能改变新任务。

**组件拆法：** `QuestionCard` 渲染正文、题目、候选预览、表单、提交以及只读回执；`InlineToolCard` 和弹框分别提供各自容器。两处共享请求快照与媒体授权，CSS 随 Core 组件作用域加载。

## 5. 首版题型与内容

- 题型是单选、多选、文本和确认/退回；支持多题同卡、必要时带备注。确认大纲用正文 Markdown + 确认/退回 + 选填修改意见；保留专用大纲编辑器作为后续独立题型，首版不承诺原 PPT 的逐页专用编辑能力。
- 媒体预览是独立维度，**问题正文和每个选项均可包含** Markdown、单图、图组、静态 `.html`。选择图组返回该方案的 ID。题型由答案结构决定。两处卡身都提供完整预览和作答，视觉以 PPT 工作流为基线。
- 新的媒体块与新的题型分别演进。首版不要求新做视频/音频专用预览；通用 Worker 切换前盘点现有音视频/文件协议和展示能力，已支持的行为需保留等价展示或明确商定迁移时机，不静默丢弃。未实现的新类型在 Host 登记时明确拒绝，不创建等待。
- 媒体内容使用工作区相对路径或受支持的会话素材引用。浏览器收到 Core 按请求授权的资源引用，不提供按任意路径读取的接口。HTML 首版只做静态预览：隔离 iframe，禁脚本、表单、外链请求和父页面交互，答案控件留在 Core 卡片里。不要把 HTML 插入会话 DOM 或执行文件；无法预览时列出素材失败状态并提供可理解的文本替代。

## 6. 非阻塞报告与通用 Worker 改造

`report(running)` 不等待用户，`ask` 等待答案。`completed` / `failed` 仍由 Orchestrator 校验、持久化并处理投递，Core 不持有编排状态。完成报告保留 `result`、`artifacts`、`header`、`progressNote`，展示卡改为可选 `uiRef`。扩展以带类型和版本的 payload 演进，未知事件不能触发状态迁移。

| 当前工具 | 迁移后的实现 |
|---|---|
| `task_running` | 基于 SDK 的薄适配，调用与外部 Worker 相同的 `report(running)`；有问题未答时更新进展，但不解除待答。 |
| `task_input_required` | 保留模型侧工具名与必要参数，映射为 Core 卡并 `await ask`。结构化答案映射回现有工具结果；新请求只走 Core 的等待和作答。原 pending-answer、旧问答 RPC 和弹窗可退役的部分随迁移移除；历史读取按现有格式兼容。 |
| `task_completed` / `task_failed` | 暂时注入到本次受管执行。用同一报告通道提交终态，由 Orchestrator 状态机接受、持久化、安排 outbox 后才返回成功；已成功时保留现有 `concludeTurn` 语义。启动失败、手动停止和缺少终态等宿主兜底仍由 Orchestrator 结算。 |
| `task_todo` | 保留名称和日程 CRUD；共用执行身份解析，调用编排领域接口。日程不进入 Core 的公共交互协议。 |

派发时同时准备受管执行绑定、终态工具及简短结束指令（通用和专用都适用）。以可信执行身份和代次做隔离，禁止按 session 当前活跃任务推断旧工具要结算哪条任务。绑定通过可信的派发来源与实际轮次建立，不能仅按「下一个在此会话的调用」绑定，尤其是 followup 排队和改单场景。运行时如果只能把定义注册在 agent scope，也须在模型可见工具/执行闸门按受管轮次启用，轮次完成、取消或失效则撤销，独立轮次不可调用。普通 `ask`/`report(running)` 不需要 Orchestrator 能力令牌；终态入口由管理方在注入时授予。保留既有 scheduled task 的按来源归因、批量报告与 `concludeTurn` 分支：确有定时任务归属的受管轮次可获得对应执行范围，不能用它为任意独立轮次开启全局终态工具。

Core → Orchestrator 的宿主事件以及卡身挂载约定见协议 §6。Orchestrator 消费后在现有串行链写状态，任务卡读取现有任务数据中的待答摘要和 `requestId`。打开弹框时只把该 ID 交给 Core；Orchestrator 不需要传预览、默认答案或表单 schema，也不自己向 Worker 回写答案。终态报告的接收回执区分「已经持久接受」与失败/重复。严禁持有编排锁等待用户、媒体或 UI 广播。若终态回执需等编排状态落盘，则在进入锁前调用报告入口，避免监听者反向等待同一把锁。产品数据和用户授权由宿主控制；PPT 工具不能用参数填写其他会话或任务的 ID。

## 7. Core 接管 GenUI：创建、引用与渲染

1. **固定上游代码。** 开工时从 [dsh-genui 的 Git 仓库](https://github.com/omdsh-dev/dsh-genui) 取最新 `main`，记录实际使用的完整 SHA、复用文件、本地改动和 MIT 许可归属。本次设计参考 [`c523e98`](https://github.com/omdsh-dev/dsh-genui/commit/c523e9848e319124d26604ae6b3bbe1a3c979cef)。从 `src/client/embed.ts` 追踪所需的解析校验、`GenuiBlock`、样式及资源；只引入展示所需代码，不跟踪浮动分支。保留图表、表格、统计、时间线等展示能力，以及展开、缩放等只影响当前视图的操作。
2. **缩减 Skill，停用旧入口。** Core 的 Skill 只描述支持的展示节点、`create_ui` 和引用方式。Host 用同一份展示组件清单递归校验，拒绝旧表单、按钮回传及 Panel 等能力。Core 不装载上游插件入口、旧工具、会话 action 回传和 Panel 注册。纯展示组件内部的局部状态可保留，无需重写整个渲染器。需要用户回答的业务依旧调用 `ask`。
3. **校验后持久化。** Host 在 `create_ui` 内校验展示规范、资源引用与大小；返回具体失败字段，不存不可渲染的半成品。持久化成功后才返回不可变的 `uiRef`。记录规范版本、所属会话、可选的受管执行代次及授权。图表等按需资源要在目标 DSH 客户端加载，历史引用在服务重启后仍可解析。
4. **两种使用方式，同一个渲染入口。** Core 识别内容只有一个 `uiRef` 的 `dsh-ui` 围栏，按会话权限加载并用同一个组件渲染。优先接入 DSH 的 Markdown 渲染扩展；如果目标版本没有插槽，只做针对该围栏的接管，不移植上游整套监听和 action 机制。流式输出未闭合时不解析引用，失效或无权访问时显示提示。Orchestrator 收到 `task_completed.uiRef` 先校验它属于当前受管执行，再持久化任务关联。按现有 outbox 投递前，给目标 Lead 会话授予只读权限；授权失败按现有规则重试，关闭投递的任务不向 Lead 自动展示。Lead 仍原样转发围栏，其中只有引用 ID。`create_ui` 由 Core 按工具作用域发布，独立会话按配置使用，Lead 与受管 Worker 的可见工具名单显式调整。
5. **同版切换。** 从 Orchestrator 依赖和 bundle 启用项移除旧 GenUI 插件；用户单独启用的旧插件也在升级时停用。同一个围栏只由 Core 渲染。新提交不再接收内联 JSON。以持久化的切换边界识别历史消息；只有切换前的 JSON 围栏和旧任务中已存的 `card` 保留只读兼容，同样停用回传和 Panel。旧待投递任务有 `card` 时，用它通过同一展示校验创建一次引用，按任务去重；不能创建时照常交付文本和制品。不批量重写聊天历史，任务卡布局维持不变。

## 8. 施工顺序与验收

| 阶段 | 可交付结果与验收 |
|---|---|
| 1. Core 契约与宿主 | DSH profile 上激活一个 Core；最小示例工具独立运行。`ask` 返回答案，未注册的题型立即拒绝；两客户端同时作答只接收一次，超时、停止和重连行为可验证。 |
| 2. 卡片与媒体 | 以 PPT 风格实现内嵌卡和独立 Dialog 框内的同一卡身。覆盖两图选一、两套图选一、正文带图与 `.html`、确认加备注，以及无媒体文本题。桌面和窄屏均能完成作答。实际验证平台工具视图和复用断点。 |
| 3. Orchestrator 接入 | 通用 Worker 工具迁移；点击现有待答入口即可在弹框作答。两处各答一次、同时答、关弹框再开、改单后旧答案拒绝；多个请求只关闭已作答项。注册第二个示例预设并用 `dispatch.type` 派发，旧 `general` 历史仍可用。 |
| 4. GenUI 切换与终态 | 同一个 `uiRef` 经正文和 `task_completed` 渲染；重启后能回看，猜测其他会话 ID 或提交旧执行引用被拒绝。覆盖校验失败、旧 JSON 只读、旧任务待投递、资源加载和重复投递。验证 `silent`、定时来源、改单、手停、制品交付与 `concludeTurn` 无回归；旧插件入口停用后，Core 的 `ask` 仍可双路作答。 |
